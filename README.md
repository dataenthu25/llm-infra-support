# opspilot

Ask questions about ops runbooks and postmortems. Answers are generated by a local LLM
from the most relevant runbook chunks, stored as embeddings in Postgres + pgvector,
and every bullet cites its source file.

## Setup

```bash
brew install uv                  # once: https://docs.astral.sh/uv/
uv sync                          # .venv with Python 3.12 + dependencies
cp .env.example .env             # optional: override defaults (LLM, threshold, DB)
docker compose up -d             # Postgres 17 + pgvector on localhost:5433
ollama pull qwen2.5:7b           # or point LLM_BASE_URL/LLM_MODEL at another endpoint
uv run opspilot-ingest           # chunk, embed and store data/runbooks/*.md
```

## Run

```bash
uv run uvicorn opspilot.api:app --reload      # API docs at http://localhost:8000/docs

curl -s -X POST localhost:8000/ask -H 'content-type: application/json' \
  -d '{"question": "Our postgres replica is 5 minutes behind. What should I check?"}'

uv run python scripts/search.py "question"    # retrieval only, top 3 chunks with distances
uv run python scripts/benchmark.py            # fixed question set -> results table below
uv run pytest                                 # chunking and tracing tests
```

## Tracing (optional)

Set `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` in `.env` and every `POST /ask` sends a
trace to [Langfuse](https://langfuse.com). Without them the app runs exactly as before.

To run Langfuse locally (needs ~4 GB of RAM for Docker):

```bash
cp langfuse/.env.example langfuse/.env   # replace every CHANGEME (openssl rand -hex 32)
cd langfuse && docker compose up -d      # UI at http://localhost:3000 after ~2-3 minutes
# in the project root .env: LANGFUSE_PUBLIC_KEY / LANGFUSE_SECRET_KEY =
#   LANGFUSE_INIT_PROJECT_PUBLIC_KEY / _SECRET_KEY from langfuse/.env
```

`langfuse/docker-compose.yml` is Langfuse's official self-hosting file. It is kept in its own
folder so it reads `langfuse/.env`, not opspilot's `.env` (both define `DATABASE_URL`).
`LANGFUSE_INIT_*` creates the org, project, login and API keys on first start.

| Service | What it does |
|---|---|
| `langfuse-web` (:3000) | UI and API. Receives traces from the SDK, stores the raw events in MinIO and queues them in Redis. |
| `langfuse-worker` | Takes queued events and writes traces into ClickHouse. Also runs evaluations and exports. |
| `postgres` | Users, projects, API keys, prompts, settings. Separate from opspilot's pgvector database. |
| `clickhouse` | Traces, observations and scores; serves the dashboards and filters. |
| `redis` | Queue between web and worker, plus cache. |
| `minio` (:9090) | S3-compatible storage for raw events, media and exports. |

Each trace is named `ask`, comes from service `opspilot` (`resourceAttributes.service.name`),
is tagged `model:<LLM_MODEL>` and `threshold:<DISTANCE_THRESHOLD>`, and contains:

- `embed-question` (embedding): the question and the embedding model.
- `vector-search` (retriever): source, section and distance of each returned chunk.
- `llm` (generation): model, temperature, full prompt, answer, input/output tokens.
- or, when the distance threshold refuses the question, a `refused` event with the closest
  distance and the near misses, and the trace is also tagged `refused` (filter on it to tune
  the threshold).

Langfuse can never break or slow down `/ask`: spans are queued in memory and sent by a
background thread, so an unreachable Langfuse only logs export errors (a request added
no measurable time in `tests/test_tracing.py`). The queue holds 2048 spans and drops the
rest. On shutdown, queued traces are flushed, but for at most 5 s, so a Langfuse outage
can't hold up a deploy.

## Architecture

```
Ingestion (offline, uv run opspilot-ingest)
  data/runbooks/*.md ─► front matter (team) ─► split on headings ─► cut long sections
                     ─► sentence-bounded overlap ─► bge-small embeddings ─► pgvector `chunks`

Question answering (POST /ask)
  question ─► bge-small embedding (with BGE query prefix)
           ─► pgvector top 4 by cosine distance (<=>, HNSW index)
           ─► closest distance > 0.45?  yes ─► "I don't have a runbook for that",
           │                                   sources [], near misses logged, no LLM call
           └► no ─► prompt: passages labelled by file + strict answer rules
                  ─► OpenAI-compatible LLM (Ollama qwen2.5:7b by default)
                  ─► answer + sources + timings + token counts
```

- **Chunking** (`chunking.py`): one chunk per heading section, so each chunk is about one
  topic. Each chunk starts with its heading path (`Doc > Section > Subsection`), then up to
  150 characters of whole sentences from the previous chunk. Code blocks are never used as overlap.
  `tests/test_chunking.py` checks that chunking never glues words together or drops any.
- **Storage** (`db.py`): one row per chunk with `source`, `section`, `team`, `content` and a
  384-dimension `embedding`, plus an HNSW index for cosine distance.
- **Retrieval** (`retrieval.py`): shared by the API and `scripts/search.py`, so both
  retrieve identically.
- **API** (`api.py`): models are loaded once at startup. The distance threshold stops
  off-topic questions before they cost an LLM call. The prompt makes the model answer in
  bullets, end each bullet with `[source-file.md]`, and add a "Not covered by the runbooks"
  bullet for any part of the question the context doesn't answer.
- **Config** (`config.py`, `.env`): database URL, LLM endpoint/model, `TOP_K`,
  `DISTANCE_THRESHOLD` and the optional Langfuse keys.
- **Tracing** (`tracing.py`): creates the Langfuse client (or a disabled one) and flushes it
  on shutdown with a time limit.

## Results

`scripts/benchmark.py`, one run per question after a warm-up call, on an Apple M4 with
Ollama running locally. Retrieval = embedding the question + pgvector query (including
opening a DB connection). Generation = the LLM call. Cited bullets = bullets ending with a
retrieved file name, or a "Not covered" bullet.

| Question | Retrieval ms | Generation ms | Tokens in | Tokens out | Model | Cited bullets |
|---|---:|---:|---:|---:|---|---:|
| Our postgres replica is 5 minutes behind. What should I check? | 67 | 2680 | 1047 | 57 | qwen2.5:7b | 2/2 |
| Pods keep getting OOMKilled after a deploy. What do I do? | 54 | 10326 | 757 | 171 | qwen2.5:7b | 3/3 |
| Clients get 502 errors from the load balancer during deploys. Why? | 83 | 4790 | 840 | 44 | qwen2.5:7b | 1/1 |
| Small requests work but large uploads hang over the VPN. What's wrong? | 108 | 9383 | 987 | 131 | qwen2.5:7b | 2/2 |
| The Redis sessions cluster is full. How do I fix it, and what is the on-call phone number? | 92 | 6238 | 1020 | 58 | qwen2.5:7b | 2/2 |
| Who is Donald Trump? | 253 | 0 | 0 | 0 | - (not called) | - |

What the numbers show:

- **Generation dominates latency.** Retrieval takes about 50-110 ms, while the LLM call
  takes 3-10 s and grows with output length.
- **The guardrail works.** The off-topic question's closest chunk had distance 0.61,
  well above 0.45, so no tokens were spent. On-topic questions scored about 0.18-0.30 in
  earlier tests.
- **The citation format held.** All 10 answer bullets ended with a retrieved file name or a
  "Not covered" line, and the unanswerable part of the Redis question (phone number) was
  flagged as not covered.
- **Answer quality is uneven with a 7B model.** The 502 answer gives the `preStop` fix but
  skips the main cause the runbook describes (keep-alive timeout mismatch). The VPN answer
  includes an irrelevant bullet and never names the root cause (MTU mismatch with ICMP
  blocked). The "Cited bullets" column checks format, not correctness.
