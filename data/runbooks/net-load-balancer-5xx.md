# Load balancer returning 502/503/504

## Overview

A spike in 5xx responses at the load balancer (ALB) with no matching errors in application logs
usually means the load balancer could not get a valid response from any target. The status code
tells you which kind of failure it was.

**Alert:** `ALB5xxRateHigh` (more than 1% of requests for 5 minutes).

## What each code means

| Code | Generated by | Meaning                                                            |
|------|--------------|--------------------------------------------------------------------|
| 502  | ALB          | Target closed the connection or sent an invalid response           |
| 503  | ALB          | No healthy targets in the target group                             |
| 504  | ALB          | Target did not respond within the idle timeout (60s default)       |
| 5xx  | Target       | Application returned the error; appears in app logs too            |

Check the CloudWatch metrics `HTTPCode_ELB_5XX_Count` (from the ALB itself) vs
`HTTPCode_Target_5XX_Count` (from your app) to know which side to investigate.

## Diagnosis

### 503: no healthy targets

```bash
aws elbv2 describe-target-health --target-group-arn <arn> \
  --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State,TargetHealth.Reason]' \
  --output table
```

Common reasons: the health check path returns non-200 after a deploy, the security group no
longer allows the ALB to reach the target port, or all pods are restarting at once.

### 502: connection reset by target

The classic cause is a keep-alive mismatch. If the application's HTTP keep-alive timeout is
shorter than the ALB idle timeout, the app closes an idle connection at the same moment the ALB
sends a new request on it. Set the app's keep-alive timeout **longer** than the ALB's
(for example 65s vs 60s). Node.js defaults to 5 seconds and is frequently affected.

Also check for pods being terminated without a `preStop` delay: the ALB keeps sending traffic
for a few seconds after a pod starts shutting down.

### 504: timeout

Slow downstream dependency or a request that legitimately takes longer than 60s. Look at
the application's own latency histogram and traces for the affected endpoint.

## Mitigation

- Roll back the last deploy if the errors started with it.
- For 503s caused by a bad health check, temporarily point the health check at a simpler path.
- For 502s during deploys, add `preStop: sleep 15` and set `terminationGracePeriodSeconds`
  above that value.
